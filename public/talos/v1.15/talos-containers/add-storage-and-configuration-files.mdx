A Talos Container's filesystem holds only its image, and anything the container writes there is lost when it stops.
This page explains how to give a container storage that persists, temporary storage, files from the host, configuration files, and a raw block device.
For more information, see the [`ContainerConfig` reference](../reference/configuration/container/containerconfig).

## Choose a mount type

The `mounts` field lists the filesystems that Talos mounts into a container.

Each entry sets one of the following sources:

- **`volume`**: A volume declared by a [`UserVolumeConfig`](../reference/configuration/block/uservolumeconfig), [`ExistingVolumeConfig`](../reference/configuration/block/existingvolumeconfig), or [`ExternalVolumeConfig`](../reference/configuration/block/externalvolumeconfig) document. Its data persists when the container stops and when the machine reboots.
- **`tmpfs`**: An in-memory filesystem. Its contents are lost when the container stops.
- **`hostPath`**: An existing path on the host.

Each entry also sets a `destination`, which is the path inside the container.
Mounts are writable unless their `options` include `ro`.

## Store data in a volume

A volume keeps a container's data across restarts, updates, and reboots.
Talos mounts each volume at `/var/mnt/<name>` on the host, and a container that mounts a volume waits for it before it starts.

**Example:** The following documents declare a user volume named `data` on an NVMe disk, and mount it into a container at `/data`:

```yaml
apiVersion: v1alpha1
kind: UserVolumeConfig
name: data
provisioning:
  diskSelector:
    match: disk.transport == 'nvme'
  maxSize: 10GiB
---
apiVersion: v1alpha1
kind: ContainerConfig
name: my-app
image: registry.example.com/my-app@sha256:...
mounts:
  - volume:
      name: data
      destination: /data
```

Talos rejects a configuration in which a container mounts a volume that no document declares.
[User Volumes](../configure-your-talos-cluster/storage-and-disk-management/disk-management/user) explains how to declare a user volume.

An existing partition or a volume created outside of Talos is mounted the same way, by the name of its `ExistingVolumeConfig` or `ExternalVolumeConfig` document.
A volume that its document declares read-only must be mounted with the `ro` option.

### Write to a volume as a non-root user

Talos creates the volume's directory owned by root, with mode `0755`, so a container that runs as another user can't write to it.

A container that runs once as root can prepare a directory for that user first.
Under the default `restricted` profile, that container needs the `CHOWN` capability to change the directory's owner.
The application container then waits for it to succeed, as described in [Configure Startup Order](./configure-startup-order).

**Example:** The following documents create `/data/app` for uid and gid 65534, and start `my-app` as that user once the directory is ready:

```yaml
apiVersion: v1alpha1
kind: ContainerConfig
name: prepare-data
image: docker.io/library/busybox:1.37
args: ["sh", "-c", "mkdir -p /data/app && chown 65534:65534 /data/app"]
mounts:
  - volume:
      name: data
      destination: /data
security:
  capabilities:
    add:
      - CHOWN
lifecycle:
  restart:
    policy: never
---
apiVersion: v1alpha1
kind: ContainerConfig
name: my-app
image: registry.example.com/my-app@sha256:...
runAs:
  uid: 65534
  gid: 65534
mounts:
  - volume:
      name: data
      destination: /data
lifecycle:
  dependsOn:
    containers:
      - name: prepare-data
        condition: succeeded
```

## Use temporary storage

A `tmpfs` mount gives a container a writable directory in memory.
It suits temporary files, because the default `restricted` profile makes the container's root filesystem read-only.
Its contents are lost when the container stops.

The `size` field limits how much the mount can hold, and a process that writes more gets a `No space left on device` error.
Without `size`, the kernel default applies.

**Example:** The following document gives a container a 64 MiB `tmpfs` mount at `/tmp`:

```yaml
apiVersion: v1alpha1
kind: ContainerConfig
name: my-app
image: registry.example.com/my-app@sha256:...
mounts:
  - tmpfs:
      destination: /tmp
      size: 64MiB
```

## Mount a path from the host

A `hostPath` mount makes an existing path on the host visible inside the container.
It can expose any part of the host, so it gives the container the widest access of the three mount sources.

The path must exist when the container starts.
Talos doesn't create it, and a container whose source path is missing fails to start and is restarted in a loop.
To make the container wait for the path instead, list it in `lifecycle.dependsOn.paths`, as described in [Configure Startup Order](./configure-startup-order).

**Example:** The following document mounts the host's `/var/log` directory into a container, read-only:

```yaml
apiVersion: v1alpha1
kind: ContainerConfig
name: log-reader
image: registry.example.com/log-reader@sha256:...
mounts:
  - hostPath:
      source: /var/log
      destination: /host/var/log
      options:
        - ro
```

## Add a configuration file

Talos has no dedicated way to pass a file to a container.
An [`EtcFileConfig`](../reference/configuration/runtime/etcfileconfig) document writes a file under `/etc` on the host, and a `hostPath` mount makes it visible in the container.

Mount the file's directory rather than the file itself.
Talos replaces the file when its contents change, and a container that mounts only the file keeps seeing the old version until it is started again.
A container that mounts the directory sees the new version.

**Example:** The following documents write `/etc/my-app/config.yaml` on the host, and mount the `/etc/my-app` directory into a container, read-only:

```yaml
apiVersion: v1alpha1
kind: EtcFileConfig
name: my-app/config.yaml
mode: 0o644
contents: |
  listen: 0.0.0.0:8080
---
apiVersion: v1alpha1
kind: ContainerConfig
name: my-app
image: registry.example.com/my-app@sha256:...
mounts:
  - hostPath:
      source: /etc/my-app
      destination: /etc/my-app
      options:
        - ro
```

Talos creates the `my-app` directory under `/etc` when it writes the file.
The file's contents are part of the machine configuration, so they have the same protection as the rest of it, as described in [How Talos Containers Work](./how-talos-containers-work#secrets).

## Give a container a block device

A [raw volume](../configure-your-talos-cluster/storage-and-disk-management/disk-management/raw) is a partition that Talos creates but doesn't format, declared by a [`RawVolumeConfig`](../reference/configuration/block/rawvolumeconfig) document.
The `devices` field gives a raw volume to a container as a block device.

The container gets a device node at the destination under `/dev`, and can read and write that device and no other.
It keeps its security profile, so the default `restricted` profile works.
The device node keeps the owner and mode of the device on the host, which are root and `0600`, so the container must run as root to use it.

A raw volume can be given to one container only, and the container waits for the volume before it starts.

**Example:** The following documents declare a raw volume named `block-data` of up to 10 GiB, and give it to a container as `/dev/data`:

```yaml
apiVersion: v1alpha1
kind: RawVolumeConfig
name: block-data
provisioning:
  diskSelector:
    match: disk.transport == 'nvme'
  maxSize: 10GiB
---
apiVersion: v1alpha1
kind: ContainerConfig
name: storage-agent
image: registry.example.com/storage-agent@sha256:...
devices:
  - rawVolume:
      name: block-data
      destination: /dev/data
```
