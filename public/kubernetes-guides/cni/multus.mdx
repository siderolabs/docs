title: "Deploy Multus CNI"
description: "Learn how to install and configure Multus CNI on Talos Linux to attach multiple network interfaces to a pod."
---

[Multus CNI](https://github.com/k8snetworkplumbingwg/multus-cni) is a container network interface (CNI) plugin for Kubernetes that enables attaching multiple network interfaces to pods.
Typically, in Kubernetes each pod only has one network interface (apart from a loopback). With Multus, you can create a multi-homed pod that has multiple interfaces.
This is accomplished by Multus acting as a "meta-plugin", a CNI plugin that can call multiple other CNI plugins.

This guide covers:

- **Install and configure Multus for Talos**: The upstream Multus DaemonSet assumes a network namespace path that doesn't match Talos's filesystem layout, so it needs a Talos-specific patch before pod networking will work correctly.
- **Configure a multi-homed pod**: Define a NetworkAttachmentDefinition and attach it to a pod, giving it a second network interface. This is the actual point of installing Multus.
- **Known issues**: Current upstream bugs and their workarounds.
- **Compatibility notes**: What changes when running Multus alongside KubeVirt or Cilium.

## Install and configure Multus for Talos

1. Deploy the `thick` DaemonSet with `kubectl`:

   ```bash
   kubectl apply -f https://raw.githubusercontent.com/k8snetworkplumbingwg/multus-cni/master/deployments/multus-daemonset-thick.yml
   ```

   This creates a DaemonSet and a CRD, `NetworkAttachmentDefinition`, which you'll use to specify your network configuration in [Configure a multi-homed pod](#configure-a-multi-homed-pod).

2. Patch the DaemonSet for Talos. The upstream manifest mounts the `host-run-netns` volume at `/run/netns`, but Talos mounts network namespaces at `/var/run/netns` instead, so edit the DaemonSet and change the volume path:

   ```yaml
   ...
           - name: host-run-netns
             hostPath:
               path: /var/run/netns/
   ```

Skipping this patch leaves your cluster crippled. Existing pods keep running, but new pods and deployments fail to schedule.
</Warning>

## Configure a multi-homed pod

Installing Multus doesn't do anything on its own: A pod only gets a second network interface once you define a NetworkAttachmentDefinition and attach it to that pod.

1. Create a NetworkAttachmentDefinition. This configures the bridge that a pod's second interface attaches to:

   ```yaml
   apiVersion: "k8s.cni.cncf.io/v1"
   kind: NetworkAttachmentDefinition
   metadata:
     name: macvlan-conf
   spec:
     config: '{
         "cniVersion": "0.3.0",
         "type": "macvlan",
         "master": "eth0",
         "mode": "bridge",
         "ipam": {
           "type": "host-local",
           "subnet": "192.168.1.0/24",
           "rangeStart": "192.168.1.200",
           "rangeEnd": "192.168.1.216",
           "routes": [
             { "dst": "0.0.0.0/0" }
           ],
           "gateway": "192.168.1.1"
         }
       }'
   ```

   This example uses `macvlan` as the bridge type. There are three types available:

   - **`bridge`** connects two Ethernet segments together in a protocol-independent way. Packets are forwarded based on Ethernet address rather than IP address, so all protocols pass through transparently at Layer 2. For containers or VMs, a bridge connects each one's virtual interface to the host network, letting them communicate.
   - **`macvlan`** creates virtual network interfaces that appear as distinct physical devices, each with its own MAC address. The underlying interface routes traffic to each virtual interface separately, so each macvlan interface can have its own IP subnet and routing. This suits containers or VMs that need the same network access as the host.
   - **`ipvlan`** is similar to `macvlan`, but shares the parent's MAC address, which needs less configuration from the networking equipment. This is useful where MAC address control or limits are in place. It offers two modes: L2 (default, behaves like macvlan) and L3 (routing-based traffic isolation instead of bridged).

   If you use the `bridge` type, also configure a bridge on your Talos nodes. Replace `<INTERFACE_NAME>` with your node's actual interface (for example, `eno1`):

   ```yaml
   machine:
     network:
       interfaces:
         - interface: br0
           addresses:
             - 172.16.1.60/24
           bridge:
             stp:
               enabled: true
             interfaces:
               - <INTERFACE_NAME>
           routes:
             - network: 0.0.0.0/0 # The route's network (destination).
               gateway: 172.16.1.254 # The route's gateway (if empty, creates link scope route).
               metric: 1024 # The optional metric for the route.
   ```

   See the [Multus bridge documentation](https://github.com/k8snetworkplumbingwg/multus-cni/tree/master/docs) for more on configuring bridges.

2. Attach the NetworkAttachmentDefinition to a pod or deployment. Reference it by name in the pod's annotations:

   ```yaml
   apiVersion: v1
   kind: Pod
   metadata:
     name: samplepod
     annotations:
       k8s.v1.cni.cncf.io/networks: macvlan-conf
   spec:
     containers:
     - name: samplepod
       command: ["/bin/ash", "-c", "trap : TERM INT; sleep infinity & wait"]
       image: alpine
   ```

## Known issues

The following are known issues when running Multus on Talos Linux. Each entry includes a workaround where one exists; these are pinned to the date they were last verified, so check the linked issue for current status before relying on them.

- **`install-multus-binary` race condition after reboot** (last verified March 21, 2025): A [known bug](https://github.com/k8snetworkplumbingwg/multus-cni/issues/1221) in the `install-multus-binary` container can cause race problems after a node reboot. Patch the container's command:

  ```yaml
        initContainers:
          - name: install-multus-binary
            command:
              - "/usr/src/multus-cni/bin/install_multus"
              - "-d"
              - "/host/opt/cni/bin"
              - "-t"
              - "thick"
  ```

- **Primary CNI plugin OOM-killed** (last verified February 3, 2025): The default 50Mi memory limit on the `kube-multus-ds` DaemonSet is too low, which can [OOM-kill the primary CNI plugin](https://github.com/k8snetworkplumbingwg/multus-cni/issues/1346). Increase the resource limits on the DaemonSet's container:

  ```yaml
    resources:
      limits:
        cpu: 300m
        memory: 150Mi
      requests:
        cpu: 200m
        memory: 100Mi
  ```

- **ARM64 images built incorrectly** (last verified July 29, 2024): The [official Multus images](https://github.com/k8snetworkplumbingwg/multus-cni/issues/1251) are built incorrectly for ARM64. Self-building the image is an adequate workaround for now.

## Compatibility notes

Running Multus alongside certain other tools requires extra configuration. This section covers KubeVirt and Cilium specifically. If you're not using either, you can skip it.

### Using Multus with KubeVirt

If you want to use KubeVirt and expose a virtual machine to the outside world with Multus, configure the `bridge` type instead of `macvlan` or `ipvlan`; neither works for this case.

<Note>
The KubeVirt documentation lists `macvlan` and `ipvlan` as invalid CNIs for secondary networks using a bridge interface, since a bridge interface moves the pod interface's MAC address to the VM, leaving the pod interface with a different address, but `macvlan` and `ipvlan` require the pod interface to keep its original MAC address.
</Note>

See the [KubeVirt documentation](https://kubevirt.io/user-guide/virtual_machines/interfaces_and_networks/#invalid-cnis-for-secondary-networks) for details.

### Using Cilium with Multus

Cilium needs two adjustments to work correctly alongside Multus.

#### Missing CNI reference plugins (Talos < v1.8)

Cilium doesn't ship the CNI reference plugins that most Multus setups expect (for example, `macvlan`).

<Note>
Starting with Talos v1.8, the essential CNI plugins are bundled with Talos Linux itself, so Multus and most CNIs work with Talos's bundled plugins out of the box. You generally don't need the `siderolabs/install-cni` image below anymore; it's kept here for historical context and for cases with a custom plugin requirement. For additional or custom CNI plugins, use the official upstream builds or build your own plugin image and deploy it with a DaemonSet. CNI plugins are distributed as static binaries, so they're generally compatible across Talos versions.
</Note>

If you're on an older Talos version, or need a custom plugin, extend the DaemonSet with an additional init container using a kustomize strategic-merge patch. Replace `<TALOS_VERSION>` with your Talos version:

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: kube-multus-ds
  namespace: kube-system
spec:
  template:
    spec:
      initContainers:
      - command:
        - /install-cni.sh
        image: ghcr.io/siderolabs/install-cni:<TALOS_VERSION>
        name: install-cni
        securityContext:
          privileged: true
        volumeMounts:
        - mountPath: /host/opt/cni/bin
          mountPropagation: Bidirectional
          name: cnibin
```

#### Exclusive CNI

By default, Cilium is an exclusive CNI: It removes other CNI configuration files. When using Multus, disable this by setting the Helm variable `cni.exclusive=false`. See the [Cilium documentation](https://docs.cilium.io/en/stable/network/kubernetes/configuration/#adjusting-cni-configuration) for more.
