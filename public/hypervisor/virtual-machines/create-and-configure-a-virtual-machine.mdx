Each virtual machine is described by a [`VirtualMachineConfig`](../../talos/v1.15/reference/configuration/hypervisor/virtualmachineconfig) document in the host's machine configuration. Talos creates the virtual machine from the document and keeps it matching the document.

A document is added to the host with `talosctl patch machineconfig`. For a full walkthrough, see [Run your first virtual machine](../getting-started/run-your-first-virtual-machine).

This page describes each setting in the document, how to check a virtual machine's status, how to start, stop, and reboot a virtual machine without changing the document, and how to remove a virtual machine.

## Example configuration

The following document describes a virtual machine named `vm1`. It has two virtual CPUs and 2 GiB of memory, boots from an ISO in the content library `images`, has its serial console enabled, and connects to the host link `eth0`:

```yaml
apiVersion: v1alpha1
kind: VirtualMachineConfig
name: vm1
powerState: running
cpu:
  count: 2
memory:
  size: 2GiB
firmware:
  type: bios
disks:
  - name: install
    type: cdrom
    bootOrder: 1
    provision:
      fromImage:
        library: images
        file: metal-amd64.iso
console:
  serial:
    enabled: true
networking:
  interfaces:
    - name: nic0
      link: eth0
```

Every document needs `name`, `powerState`, `cpu`, `memory`, and `firmware`. The other sections are optional.

The `name` identifies the virtual machine in Talos resources and `talosctl` commands. It can contain only ASCII letters, digits, and hyphens, and can be up to 63 characters long.

## Virtual machine settings

Each section below covers one part of the document.

### Power state

The `powerState` field sets the state Talos keeps the virtual machine in:

- `running` starts the virtual machine and keeps it running.
- `stopped` turns off the virtual machine immediately, without a clean shutdown of the guest, and removes it from libvirt. Setting `powerState` back to `running` starts it again.

The field also accepts `suspended`, but Talos does not support it. A virtual machine set to `suspended` reports the `error` stage and stays as it is.

To start, stop, or reboot a virtual machine without changing the document, see [Start, stop, and reboot a virtual machine](#start-stop-and-reboot-a-virtual-machine).

### Processors

The `cpu.count` field sets how many virtual CPUs the guest sees. The other processor settings are optional:

```yaml
cpu:
  count: 4
  limit: 2000m
  topology:
    sockets: 1
    cores: 2
    threads: 2
    pinning:
      vcpus:
        - vcpu: 0
          cpus: "8"
        - vcpu: 1
          cpus: "9-10"
      emulator: "0-1"
```

- `limit` caps how much host CPU time the virtual machine can use, in millicores. `1000m` is one host core. For example, a guest with four virtual CPUs and a `2000m` limit sees four processors, but gets at most two cores of host time. Without a limit, the virtual machine is limited only by its number of virtual CPUs.
- `topology` sets how the guest sees its virtual CPUs: as sockets, cores per socket, and threads per core. Set all three or none. Multiplied together, they must equal `count`.
- `topology.pinning` ties virtual CPUs to specific host CPUs, given as Linux CPU lists such as `8` or `9-10`. Pinning works without `sockets`, `cores`, and `threads`, and does not reserve the host CPUs for this virtual machine.
  - Each entry in `vcpus` pins one virtual CPU, counted from `0`. A virtual CPU without an entry can run on any host CPU.
  - `emulator` pins the rest of the virtual machine's threads.

To choose which host CPUs to pin, see <a href={`../../talos/v1.15/configure-your-talos-cluster/system-configuration/numa`}>NUMA Topology and VM Placement</a>.

### Memory

The `memory.size` field sets how much memory the guest has when it boots, such as `2GiB`. The other memory settings are optional:

```yaml
memory:
  size: 4GiB
  ballooning:
    enabled: true
  numa:
    mode: strict
    nodes: "1"
```

- `ballooning.enabled` adds a virtio balloon device to the guest. Talos does not set a balloon target.
- `numa` keeps the guest's memory on specific host NUMA nodes, given as a Linux node list such as `1` or `0-1`. The `mode` field sets how strict this is:
  - `strict`, the default, fails memory requests that the listed nodes cannot serve.
  - `preferred` falls back to other nodes.
  - `interleave` spreads memory across the listed nodes.

To choose NUMA nodes, see <a href={`../../talos/v1.15/configure-your-talos-cluster/system-configuration/numa`}>NUMA Topology and VM Placement</a>.

### Firmware

The `firmware.type` field sets the firmware the guest boots with: `bios` or `uefi`. On arm64 hosts, only `uefi` works. Talos accepts `bios` on arm64, but the virtual machine then fails to start.

A guest installed with one firmware type does not boot with the other. Keep `firmware.type` the same after a guest is installed.

To boot the guest with secure boot, set `firmware.secureBoot.enabled` to `true`. Secure boot needs `uefi`.

### Hardware profile

The `profile` field sets the hardware the guest sees: its machine type, which is the emulated chipset, and its CPU model. Talos includes three profiles on amd64 hosts:

- `host`, the default when `profile` is not set, uses the `q35` machine type and a CPU model that matches the host's CPU, with libvirt's `host-model` mode.
- `passthrough` uses the `q35` machine type and shows the guest the host's CPU as it is, with libvirt's `host-passthrough` mode.
- `legacy` uses the older `pc-i440fx-9.2` machine type and the basic `kvm64` CPU model, for guests that need a traditional PC chipset.

For example, the following setting gives a guest the host's CPU as it is:

```yaml
profile: passthrough
```

A change of profile, or a change to the profile a virtual machine uses, does not affect a running guest, and rebooting the guest does not apply it either. It applies the next time the virtual machine is stopped and started, for example with `talosctl hypervisor stop` and `talosctl hypervisor start`, as described in [Start, stop, and reboot a virtual machine](#start-stop-and-reboot-a-virtual-machine).

A virtual machine that names a profile that does not exist stays at the `pending` stage until the profile is defined.

#### Custom profiles

A [`VirtualMachineProfileConfig`](../../talos/v1.15/reference/configuration/hypervisor/virtualmachineprofileconfig) document defines a profile of your own. It is added to the host's machine configuration like a `VirtualMachineConfig` document.

The following document defines a profile named `rack-a-compat`, with a versioned `q35` machine type and the `Haswell-noTSX-IBRS` CPU model without the `pku` feature:

```yaml
apiVersion: v1alpha1
kind: VirtualMachineProfileConfig
name: rack-a-compat
machine: pc-q35-9.2
cpu:
  mode: custom
  model: Haswell-noTSX-IBRS
  features:
    - name: pku
      policy: disable
```

The document has the following fields:

- `name` is the name that virtual machines use in their `profile` field. The names `host`, `legacy`, and `passthrough`, and names that start with `compat-`, are reserved.
- `machine` is `q35`, `pc`, or a versioned machine type that starts with `pc-q35-` or `pc-i440fx-`, such as `pc-q35-9.2`. A versioned machine type keeps the guest's hardware the same when QEMU is updated, while `q35` and `pc` follow the newest version.
- `cpu.mode` is `host-model`, `host-passthrough`, or `custom`. The other `cpu` fields work only with `custom`:
  - `model` names the CPU model, and is required.
  - `fallback` is `forbid`, the default, or `allow`. With `allow`, libvirt can use a different CPU model if the host cannot provide the one named.
  - `features` turns individual CPU features on or off. Each entry has a `name` and a `policy`: `require`, `disable`, `optional`, `force`, or `forbid`. For what each policy does, see the [libvirt CPU model documentation](https://libvirt.org/formatdomain.html#cpu-model-and-topology).

Talos checks only that the document is valid. It does not check that the host's CPU supports the model or features.

To list the profiles available on a host, including custom ones, run the following command, replacing `<host-ip>` with the host's IP address:

```bash
talosctl get virtualmachineprofilespecs --nodes <host-ip>
```

### Disks

Each entry in `disks` attaches a disk to the virtual machine. The `type` field sets the kind of disk:

- `disk`, the default, is a writable disk stored in a storage pool.
- `cdrom` is a read-only CD-ROM that attaches an image from a content library.

Every disk has the following fields:

- `name` identifies the disk within the virtual machine. It can contain only ASCII letters, digits, and hyphens, and can be up to 63 characters long.
- `bootOrder` sets the disk's place in the boot order, lowest first. Each value must be unique within the virtual machine. Set it on the disk the guest boots from.

To install an operating system, attach the installer ISO as a CD-ROM and a writable disk to install it to. Any ISO built for the host's processor architecture works, because a virtual machine runs on the same architecture as its host.

#### Writable disks

A writable disk is created empty in a storage pool:

```yaml
disks:
  - name: data
    pool: pool1
    size: 20GiB
    provision:
      blank: {}
```

The fields work as follows:

- `pool` names the storage pool that stores the disk. The pool must be declared in the host's machine configuration. To declare one, see [Create a storage pool](../storage/create-a-storage-pool).
- `size` sets the size of the disk, such as `20GiB`.
- `provision.blank` creates the disk empty. A writable disk cannot be created from a content library image.
- `format` sets the file format of the disk, `qcow2` by default or `raw`.
- `bus` sets the controller the disk connects to, `virtio` by default, or `scsi` or `sata`. A guest without virtio drivers needs `sata`.

Talos stores the disk as a file named `<vm-name>__<disk-name>.<format>` in the pool. The file is kept when the disk or the virtual machine is removed, and a disk with the same virtual machine name and disk name in the same pool attaches the existing file again.

The size of a disk can only grow. A larger `size` takes effect the next time no running virtual machine uses the disk, and a smaller `size` is ignored.

#### CD-ROM disks

A CD-ROM disk attaches an image from a content library, read-only:

```yaml
disks:
  - name: install
    type: cdrom
    bootOrder: 1
    provision:
      fromImage:
        library: images
        file: metal-amd64.iso
        digest: sha256:<checksum>
```

The fields work as follows:

- `provision.fromImage` names the content library and the file in it. The library must be declared in the host's machine configuration. The optional `digest` pins the file to a checksum. See [Upload and manage images](../storage/upload-and-manage-images#pin-an-image-to-a-digest).
- `bus` sets the controller the disk connects to. A CD-ROM uses `sata` by default, and can also use `scsi`. It cannot use `virtio` or `nvme`.

The image is used in place in the library, not copied. A CD-ROM disk does not accept `pool`, `size`, `format`, or `provision.fromImage.mode`.

### Consoles

A virtual machine has two consoles, both turned off by default:

- `serial` attaches a serial port, for a text console.
- `vnc` attaches a display, for a graphical console.

To turn them on, add:

```yaml
console:
  serial:
    enabled: true
  vnc:
    enabled: true
```

On amd64 hosts, turning on the VNC console also adds a VGA display, a USB keyboard, and a USB tablet. The `video` section selects a different display:

```yaml
video:
  model: bochs
  vramMiB: 64
```

- `model` is `vga` by default, or `virtio`, `bochs`, or `cirrus`.
- `vramMiB` sets the display's video memory in MiB, as a power of two. It applies only to `vga`, from 1 to 512, and `bochs`, from 4 to 256.

The `video` section has no effect on arm64 hosts or when the VNC console is off.

To use the consoles, see [Access the virtual machine console](./access-the-virtual-machine-console).

### Network interfaces

Each entry in `networking.interfaces` adds a network interface to the virtual machine. A virtual machine with no interfaces has no network connection.

```yaml
networking:
  interfaces:
    - name: nic0
      link: eth0
      hardwareAddr: "52:54:00:12:34:56"
```

- `name` identifies the interface within the virtual machine. It is not the device name inside the guest, which the guest operating system chooses.
- `link` is the name or alias of an Ethernet link on the host, such as a physical interface, a bond, or a VLAN. It can be up to 15 characters long.
- `hardwareAddr` sets the interface's MAC address. It must be a unicast address.

The interface connects to the host link through macvtap, so the guest appears on that network as a separate machine. Virtual machines on the same link can reach each other, but the host cannot reach them through that link's address.

By default, the MAC address is based on the virtual machine and interface names. It does not depend on the host, so virtual machines with the same names on different hosts get the same address. Set `hardwareAddr` when:

- Hosts that run virtual machines with the same names share a network.
- A DHCP server reserves an address for the guest.
- The address must stay the same after a rename.

### Guest setup with cloud-init

The `guest.cloudInit` section passes settings to the guest for its first boot, so the guest can set itself up without manual steps. Talos packs the settings into a small ISO labeled `CIDATA`, stores it in a content library as `cloud-init-<hash>.iso`, and attaches it to the virtual machine as a CD-ROM. The guest reads it with cloud-init. Talos replaces the ISO when the settings change, which restarts a running guest, and deletes it when the virtual machine is removed.

The following example sets the guest's hostname, an administrator account, and a fixed IP address:

```yaml
guest:
  cloudInit:
    library: images
    metaData: |
      instance-id: vm1-001
      local-hostname: vm1
    userData: |
      #cloud-config
      users:
        - name: admin
          ssh_authorized_keys:
            - ssh-ed25519 AAAAC3NzaC1lZDI1NTE5...
    networkConfig: |
      version: 2
      ethernets:
        eth0:
          addresses:
            - 192.168.1.10/24
          gateway4: 192.168.1.1
```

- `library` names the content library that stores the ISO. It is required, and the library must be declared in the host's machine configuration.
- `metaData` holds the guest's identity. Include an `instance-id`: cloud-init uses it to tell a reboot from a new virtual machine. Changing it makes the guest run its setup again. Without it, changes to `userData` may not take effect.
- `userData` holds what to set up. For most Linux distributions, this is a cloud-config document that starts with `#cloud-config`. For a Talos Linux guest, it is the guest's machine configuration.
- `networkConfig` holds network settings, for guests that cannot get them over DHCP.

At least one of `metaData`, `userData`, and `networkConfig` must be set, and together they can be up to 4 MiB. Talos stores them as plain text in the machine configuration, which only users with the Admin role can read.

A Talos Linux guest reads these settings only when it boots the `nocloud` image from Image Factory, not the `metal` image. It uses them as follows:

- `userData` is the guest's machine configuration. A document that starts with `#cloud-config` is ignored. Without a machine configuration, the guest keeps waiting for one and does not enter maintenance mode.
- The hostname in `metaData` is applied only when `networkConfig` is also set.

For more on how a Talos Linux machine uses these settings, see <a href={`../../talos/v1.15/platform-specific-installations/cloud-platforms/nocloud`}>NoCloud</a>.

The `guest.agent.enabled` field attaches a channel for the QEMU guest agent, a program that can run inside the guest. Talos reads the guest's IP addresses through this channel and shows them in the [virtual machine status](#virtual-machine-status). The channel is on by default. To remove it, set `enabled` to `false`.

### How changes are applied

A change is applied with a patch that has the document's `apiVersion`, `kind`, and `name`, and the fields to change. The patch merges into the existing document:

- Entries in `disks` are matched by name. An entry with an existing name updates that disk, and an entry with a new name adds a disk. A patch cannot remove a disk. To remove one, edit the machine configuration with `talosctl edit machineconfig`.
- The `networking.interfaces` and `cpu.topology.pinning.vcpus` lists are replaced as a whole by the list in the patch.

If a change alters a running virtual machine's definition, Talos replaces the virtual machine. This interrupts the guest, like turning it off and on again. A change that leaves the definition the same, such as setting a field to its default value, does not interrupt the guest. A change of [hardware profile](#hardware-profile) is the exception: it waits until the virtual machine is stopped and started.

Talos stops a running virtual machine when it can no longer build its definition. For example, this happens when:

- A disk's content library file is removed, or no longer matches its pinned digest.
- The host link named in `link` no longer exists.

## Check a virtual machine's status

Talos reports what it sees about each virtual machine in three resources. Replace `<host-ip>` in the following commands with the host's IP address.

### Virtual machine status

The `VirtualMachineStatus` resource shows how far each virtual machine has progressed toward its declared state:

```bash
talosctl get virtualmachinestatuses --nodes <host-ip>
```

The `POWER` column shows the power state Talos observes: `running`, `stopped`, or `unknown`.

The `STAGE` column shows the progress:

- `unknown` means Talos has not seen the virtual machine in libvirt yet.
- `pending` means Talos is still starting or stopping the virtual machine, or is waiting for something on the host, such as a host link or a disk that is not ready.
- `ready` means the virtual machine is in its declared state.
- `error` means something stops the virtual machine from reaching its declared state. For example, a writable disk is set to be provisioned from an image, the host link is not an Ethernet link, the power state is not supported, or the name is already used by a libvirt domain that Talos did not create.

The `ADDRESSES` column shows the guest's IP addresses. Talos reads them from the QEMU guest agent, so the column stays empty for a guest that does not run it.

When Talos knows what it is waiting for or what went wrong, the `ERROR` column says so.

### Disk status

The `VirtualMachineDiskStatus` resource shows each disk of each virtual machine:

```bash
talosctl get virtualmachinediskstatuses --nodes <host-ip>
```

The output has the following columns:

- `MACHINE` and `DISK` name the virtual machine and the disk.
- `POOL` is the storage pool that holds a writable disk. It is empty for a CD-ROM.
- `PHASE` is `ready` once the disk can be attached.
- `SOURCE` is the file on the host that the disk is attached from.
- `ERROR` explains why a disk is not ready, for example because its content library file is missing or does not match its pinned digest.

A virtual machine with a disk that is not ready does not start, and a running one is stopped.

### libvirt domains

libvirt calls each virtual machine a domain. The `VirtualMachineDomainStatus` resource shows every domain libvirt has on the host, including domains that Talos did not create:

```bash
talosctl get virtualmachinedomainstatuses --nodes <host-ip>
```

The output shows each domain's UUID, power state, libvirt state code, memory in KiB, and number of virtual CPUs.

To see other options for these commands, such as following changes as they happen, run:

```bash
talosctl get --help
```

## Start, stop, and reboot a virtual machine

The `talosctl hypervisor start`, `stop`, and `reboot` commands change a virtual machine's power without changing its document. Each command targets one host and needs the `os:operator` or `os:admin` role.

Replace `<host-ip>` in the following commands with the host's IP address:

- To start a virtual machine:

  ```bash
  talosctl hypervisor start vm1 --nodes <host-ip>
  ```

- To stop a virtual machine:

  ```bash
  talosctl hypervisor stop vm1 --nodes <host-ip>
  ```

  By default, Talos presses the virtual machine's power button and waits for the guest to shut itself down, pressing the button again at least 30 seconds apart until it does. While it waits, the virtual machine is at the `pending` stage. A guest that does not respond to the power button keeps running. To turn the virtual machine off immediately, without a clean shutdown of the guest, add `--graceful=false`.

- To reboot a running virtual machine:

  ```bash
  talosctl hypervisor reboot vm1 --nodes <host-ip>
  ```

  By default, Talos asks the guest to restart through the power button. With `--graceful=false`, Talos turns the virtual machine off immediately and starts it again. A virtual machine must be running and at the `ready` stage to be rebooted.

The `start` and `stop` commands override `powerState` until the host reboots. While an override is in place, changing `powerState` in the document has no effect. After the host reboots, the virtual machine follows its document again. Running `start` on a virtual machine whose document sets `powerState: running` removes the override.

To see the overrides in place, run:

```bash
talosctl get virtualmachinepoweroverrides --nodes <host-ip>
```

The `reboot` command does not change the power state, and does not apply a change of [hardware profile](#hardware-profile).

## Remove a virtual machine

To remove a virtual machine, delete its document with a patch. Talos turns the virtual machine off immediately and removes it from libvirt. Its most recent console output stays readable with `talosctl logs --kind=vm`.

Run the following command to create `vm1-delete.yaml`, a patch that deletes the `vm1` document:

```bash
cat <<'EOF' > vm1-delete.yaml
apiVersion: v1alpha1
kind: VirtualMachineConfig
name: vm1
$patch: delete
EOF
```

Apply it to the host, replacing `<host-ip>` with the host's IP address:

```bash
talosctl patch machineconfig --nodes <host-ip> --patch vm1-delete.yaml
```
